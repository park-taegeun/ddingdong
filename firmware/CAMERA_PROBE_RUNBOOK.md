# 카메라·마이크·ToF 동시 구동 관측 Runbook (`env:camera_probe`)

2026-09-17 신설. 대상 = **보드 2차 체인(카메라 캡처 + 녹음 → `/enrich`)을 붙이기 전에 답해야 하는 질문 하나**:

> **카메라(와 WiFi 송신)를 켜면 마이크 클립 미결(6.3(n))이 악화되는가?**

이 문서는 **관측 절차와 읽는 법**만 담는다. 판정 임계값·해결책(펌웨어 필터·재배선·해상도 확정·녹음 길이)은
전부 범위 밖이다 — 이 하네스는 숫자를 내고, **무엇이 악화인지는 결과를 본 사람이 정한다.**

---

## 0. 이 세션이 증명하려는 것

기존 실측(6.3(n), PR #53 댓글)에서 **ToF 측정 동작이 마이크 클립의 원인**인 것까지는 밝혀졌고,
그 안의 기전과 해결책은 **사용자 판단 대기** 상태다. 2차 체인은 여기에 **새 변수 두 개**를 더한다:

| 새 변수 | 왜 마이크를 흔들 수 있는가 | 근거유형 |
|---|---|---|
| **카메라 ON** | ① esp32-camera 의 DMA 태스크가 `CONFIG_CAMERA_CORE0=y` 로 **Core 0**(= micTask·tofTask 와 같은 코어)에 붙는다 ② 프레임버퍼가 PSRAM 이라 마이크 링버퍼와 **같은 PSRAM 버스**를 쓴다 ③ 캡처 순간 전류가 공유 3V3 를 흔든다 | ①② 실측 설치 sdkconfig·코드 대조 / ③ 논증 |
| **WiFi 송신** | 송신 버스트의 순간 전류 → 브레드보드 전원 흔들림 → 마이크 잡음·브라운아웃 재부팅 | 논증(미실측) |

⇒ 이 하네스는 두 변수를 **따로따로** 켜고 끈다. 악화되면 2차 오디오가 오염돼 STT·ML 입력이 같이 망가지므로,
배관(PR-B)을 짜기 전에 이 답이 먼저 나와야 한다.

**이 하네스가 바꾸지 않는 것**: 제품 코드 0줄(`camera_common` / `mic_common` / `tof_common` / `uplink_common` 무수정),
서버 API 호출 0, 판정·임계값 0, 6.3(n) 해결책 0.

## 1. 전제 (전부 지켜야 결과가 비교 가능하다)

- **결선 변경 금지.** 9.1(d) ToF 6가닥 + 6.3(a) 마이크 6가닥 + 카메라 FPC 그대로. 재배선은 해결책이므로 여기서 하지 않는다.
- **보드 위치 고정.** 세션 내내 같은 자리. 모드 사이에 보드를 들었다 놓으면 ToF·음향·전원 조건이 동시에 바뀐다.
- **조용한 환경.** 사람 대화 없음. 공조음은 상시 포함되어도 되지만 세션 내내 **동일**해야 한다.
- **센서 앞 1.5m 빈 공간 + 무자극.** 시작 전 `[cp] tof fr=… edge=0` 이 나오는지 확인한다 — `edge` 가 계속 증가하면 시야에 움직이는 것이 있다는 뜻이고, ToF 축이 모드가 아니라 사람에 반응하게 된다.
- **음향 포트 막힘 없음.** 마이크 위에 손·종이·케이블이 얹히면 rms 가 모드와 무관하게 내려간다.
- **핫스팟 켜져 있어야 한다.** WiFi 축(m1~m4)이 성립하려면 부팅 시 연결에 성공해야 한다. 실패하면 창 출력의 `st=` 가 3(`WL_CONNECTED`)이 아니고 `txerr` 만 올라간다 → 그 구간의 WiFi 축은 무효(8절).
- **UDP 목적지 주소에 호스트가 살아 있어야 한다(수신 프로세스는 필요 없다).** `secrets.h` 의 노트북 LAN 주소 + 포트 `55555`. 서버(5000)·`tls_probe_server`(5001) 와 겹치지 않는다. 듣는 **소켓**이 없어도 송신 부하는 그대로다 — 재는 것은 송신 동작이지 왕복이 아니다. 그러나 그 **주소에 아무 기기도 없으면** ARP 가 풀리지 않아 송신 자체가 일어나지 않는다(그런데 로그는 정상으로 보인다 — 2-1 절에서 반드시 확인한다).
- **서버·터널 불필요.** `/detect`·`/enrich` 를 부르지 않는다. 카카오·NCP 과금 0.

```

cd ~/ddingdong-측정결과/$(date +%Y-%m-%d)/camera_probe
cat > camera_probe_runtime.log << 'EOF'
```

⚠️ **키 입력은 모니터 창을 클릭해 활성화한 뒤에만 전달된다.** 다른 창에서 누르면 모드가 바뀌지 않고,
그러면 「바뀌었다고 생각한 구간」이 통째로 이전 모드 데이터가 된다. 모드를 누른 뒤 **확인 줄**(3절)이
뜨는지 반드시 눈으로 본다.

부팅 로그 기대:

```

[BOOT] reset=1 (POWERON) env=camera_probe built=Sep 17 2026 21:00:00
[MEM:boot] PSRAM total=8388608 free=… | Heap free=… min=…
[mic][M5a] ring alloc OK: 32 slots x 1024 samples = 65536 bytes (2048ms) | …
[BOOT] micProbeTask started (Core 0, prio 4)
[tof] VL53L5CX ready (8x8, 15Hz, continuous)
[BOOT] tofProbeTask started (Core 0, prio 3)
[BOOT] wifi up ip=192.168.x.x rssi=-52
[BOOT] udp dst=192.168.x.x:55555
[cp][m0] set cam=0 wifi=0 res=0 init=0 camres=0
[BOOT] ready — m0 기준선. 모드 전이는 RUNBOOK 순서표대로.
```

- `[BOOT] mic init 실패` → 마이크 축 무효. 이 세션의 목적 자체가 성립하지 않으므로 중단하고 9절.
- `[BOOT] tof init 실패` → ToF 축만 무효. 나머지는 계속 돌지만, 6.3(n) 대조가 「ToF 없는 조건」이 되므로 기록에 반드시 적는다.
- `[BOOT] wifi 연결 실패` → WiFi 축(m1~m4) 무효. 카메라 축(m5~m7)만 유효.

### 2-1. ★ 측정 전 확인 — WiFi 부하 축이 **실제로 부하를 만드는가**

이 하네스에서 WiFi 축은 조용히 죽을 수 있다. 핫스팟이 노트북에 다른 IP 를 주면 `secrets.h` 의
대상 주소에 아무 기기도 없게 되는데, 그때 lwIP 는 ARP 가 풀릴 때까지 패킷을 큐에 담고
`sendto()` 에 **성공을 돌려준다**(설치 `lwipopts.h` 의 `ARP_QUEUEING=1`). 창 출력에는 `tx` 가
올라가고 `txerr=0` 으로 보이지만 무선으로 나가는 것은 이따금의 ARP 요청뿐이다. 그 상태로 측정하면
「WiFi 송신을 켰는데 마이크가 안 흔들린다」는 **거짓 결론**이 나온다. 그래서 측정 전에 세 줄을 본다.

**① 노트북의 현재 사설 IP**

```
ipconfig getifaddr en0
```

**② 부팅 줄의 대상 주소와 같은가**

```
[BOOT] udp dst=192.168.x.x:55555     ← 이 주소가 ① 과 같아야 한다
```

다르면 `secrets.h` 의 `SPIKE_SERVER_HOST` 를 ① 값으로 고치고 **재플래시**한다(값 편집은 로컬에서만,
파일은 커밋되지 않는다). 대역 자체가 다르면 핫스팟 재접속부터 한다.

**③ m1 에서 패킷이 실제로 도착하는가 (1회, macOS 기본 도구만)**

모니터를 잠깐 두고 노트북 다른 창에서:

```
nc -u -l 55555 | head -c 2800 | wc -c
```

`2800` 이 찍히고 명령이 끝나면(= 1400B 패킷 2개) 축이 살아 있다. 몇 초가 지나도 아무것도 안 찍히면
②로 돌아간다. **확인되면 바로 끝난 명령이므로 따로 죽일 프로세스가 없다.**

> 이 확인이 관측 조건을 바꾸는가 — 아니다. ARP 는 ②가 맞는 순간 이미 풀려 있고, 듣는 소켓이 생기고
> 말고는 **보드가 내보내는 양**을 바꾸지 않는다. 바뀌는 것은 노트북이 돌려보내는 ICMP
> port-unreachable 유무뿐이라, 본 측정(m0 부터)은 이 명령이 끝난 뒤에 시작한다.

## 3. 키와 모드 (재플래시 없음 — 인접 모드끼리 한 변수만 다르다)

| 키 | 모드 | 카메라 | WiFi 송신 | 해상도 | 직전 모드 대비 바뀐 변수 1개 | 왜 재는가 |
|---|---|---|---|---|---|---|
| `0` | m0 | **OFF**(deinit) | off | QVGA | — | **기준선.** 마이크 + ToF 만 = 6.3(n) 조건 재현 |
| `1` | m1 | OFF | **ON** | QVGA | WiFi 송신 | WiFi 송신 전류 **단독** 기여 |
| `2` | m2 | **IDLE**(init만, 캡처 0) | ON | QVGA | 카메라 | init 자체(XCLK·SCCB·PSRAM 점유)의 기여 |
| `3` | m3 | **PERIODIC**(1초 1장) | ON | QVGA | 카메라 | 제품 2차 체인이 실제로 할 부하 |
| `4` | m4 | **CONT**(연속) | ON | QVGA | 카메라 | 상한 부하(스트레스) |
| `5` | m5 | CONT | **off** | QVGA | WiFi 송신 | 카메라 최대부하에서 WiFi 만 뺀다(역방향 재확인) |
| `6` | m6 | **PERIODIC** | off | QVGA | 카메라 | m3 에서 WiFi 만 빠진 조건 |
| `7` | m7 | PERIODIC | off | **VGA** | 해상도 | 설계 U2(해상도) 판단 입력 |
| `h` | — | — | — | — | — | 도움말 1줄 |

- **WiFi 연결 자체는 부팅 1회**이고 모드와 무관하다. 모드가 바꾸는 것은 **송신 부하**뿐 — 연결을 모드에 묶으면 한 전이에서 두 변수가 움직인다.
- 모드 진입 직후 확인 줄이 뜬다: `[cp][m3] set cam=2 wifi=1 res=0 init=1 camres=0`
  - `init=` 은 **지금 카메라 드라이버가 떠 있는가**, `camres=` 는 **실제 적용된 해상도**다. 요청(`res=`)과 `camres=` 가 다르면 해상도 변경이 실패한 것이므로 그 구간의 해상도 축은 무효(8절).
- 카메라를 켜고 끌 때 추가로 뜬다:
  - `[MEM:pre-init]` / `[MEM:post-init]` → 두 줄의 PSRAM free 차이 = **프레임버퍼 실점유** (설계 §4.3 의 유일한 미지수)
  - `[cp] cam init ok=1 ms=… psram_used=…` → **부팅 1회 init vs 이벤트마다 재시작**의 비용 입력(설계 U8)
  - `[cp] cam deinit err=0x0 ms=… psram_back=…` → deinit 이 PSRAM 을 실제로 돌려주는가
  - `[cp] framesize res=1 rc=0` → `rc` 가 0 이 아니면 해상도가 안 바뀐 것이다

## 4. 창 출력 (10초마다 7줄, 각 줄 ≤80B — 6.3(h)(j) 시리얼 손상 0 구간)

```
[cp][m3] win#7 t=73s cam=2 wifi=1 res=0
[cp] mic n=159744 pk=32768 rms=612 rmsx=448 clip=1831 gap=0
[cp] cam try=10 ok=10 nul=0 soi=0
[cp] cap len=5904..6432 ms=18/21/29
[cp] tof fr=149 edge=0 err=1
[cp] net st=3 rssi=-52 tx=500 txerr=0
[cp] mem psram=4063232 heap=210996 stk m=2440 t=3096 l=5012
```

| 줄 | 필드 | 뜻 |
|---|---|---|
| `win#` | `win#N t=…s` | 창 번호 · 부팅 후 경과초. `cam/wifi/res` 는 그 창의 모드 구성 |
| `mic` | `n` | 창에 누적된 샘플 수. 10초면 ≈160,000. **크게 모자라면 마이크가 굶은 것**(창 비교 불가) |
| | `pk` | 창 최대 \|진폭\|. **32768 = 클램프에 닿았다** |
| | `rms` / `rmsx` | 전체 RMS / **클램프 제외** RMS. 둘의 벌어짐 = 클램프가 통계를 끌어올린 정도 |
| | `clip` | 클램프 샘플 수(정의 = `noise_stats.h noiseIsClip`, 6.3(n) 과 같은 정의) |
| | `gap` | `i2s_read` 실패로 건너뛴 버퍼 수. **0 이 아니면 그 창은 마이크가 끊겼다** |
| `cam` | `try/ok/nul/soi` | 캡처 시도 / SOI까지 성공 / `fb_get` NULL / JPEG 아님. **항상 `try = ok+nul+soi`** |
| `cap` | `len=a..b` | 프레임 바이트 최소..최대. `ok=0` 창은 **`len=n/a ms=n/a (ok=0)`** 로 찍힌다 — 0 이 아니다 |
| | `ms=min/avg/max` | `fb_get` 소요 |
| `tof` | `fr/edge/err` | 프레임 수(15Hz면 10초에 ≈150) / presence 전이 수 / 읽기 실패 수 |
| `net` | `st` | `WiFi.status()` 원값. **3 = 연결됨.** 3이 아니면 그 창의 WiFi 축 무효 |
| | `rssi` `tx` `txerr` | 신호세기 / 창 내 UDP 송신 성공·실패 수 (창마다 0으로 리셋) |
| `mem` | `psram` `heap` | 여유 바이트 |
| | `stk m/t/l` | micTask · tofTask · loopTask 의 stack high-water free(워드 아님, 바이트) |

추출:

```
grep -a '^\[cp\]' camera_probe_runtime.log          # 창 출력 전부
grep -a '^\[cp\] mic' camera_probe_runtime.log      # 마이크 줄만
grep -a '^\[cp\]\[m' camera_probe_runtime.log       # 모드 전환 + 창 머리줄
grep -a 'MEM:' camera_probe_runtime.log             # 카메라 init/deinit PSRAM delta
grep -a 'reset=' camera_probe_runtime.log           # 재부팅 흔적
```

## 5. 절차 (모드당 창 6개 = 60초)

모드를 누르고 **창 1개를 버린다**(전이가 걸친 창은 두 모드가 섞여 있다). 이후 5창을 기록한다.

```
0 → (창1 버림) → 창5 기록
1 → (창1 버림) → 창5 기록
2 → (창1 버림) → 창5 기록
3 → (창1 버림) → 창5 기록
4 → (창1 버림) → 창5 기록
5 → (창1 버림) → 창5 기록
6 → (창1 버림) → 창5 기록
7 → (창1 버림) → 창5 기록
0 → (창1 버림) → 창5 기록      ← ★ 마지막에 기준선 복귀
```

**★ 마지막 m0 복귀가 이 절차의 핵심 장치다.** 처음 m0 와 마지막 m0 는 같은 구성이므로 값이 같은 자릿수로
돌아와야 한다. 돌아오지 않으면 세션 중 **환경이 드리프트**한 것이고(온도·공조·사람·전원), 그 세션의
모드 간 비교는 전부 무효다. m6 이 m3 와 WiFi 만 다른 것도 같은 성격의 재현성 확인 지점이다.

**기록 표** (창 1개 = 1행):

| 모드 | win# | mic n | pk | rms | rmsx | clip | gap | cam try/ok/nul/soi | cap len min..max | cap ms min/avg/max | tof fr/edge/err | net st/rssi/tx/txerr | psram | heap | stk m/t/l |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| m0 | | | | | | | | | | | | | | | |

## 6. 결과 읽는 법 — 「악화」의 **후보 신호**

⚠️ **임계값은 여기에 적지 않는다.** 아래는 「어느 줄의 어느 값을 무엇과 비교하는가」뿐이다.
판정은 표를 채운 사람이 한다.

### 6-1. 마이크 (최우선 질문)

비교는 **항상 같은 세션 안에서 모드 대 모드**로 한다. 다른 날 로그와 절대값을 비교하지 않는다.

| 비교 | 보는 값 | 무엇을 가르는가 |
|---|---|---|
| m0 ↔ m1 | `clip` · `pk` · `rms`/`rmsx` 차 | **WiFi 송신 단독** 기여 |
| m1 ↔ m2 | 같음 | **카메라 init 자체**(캡처 없이 드라이버만) |
| m2 ↔ m3 | 같음 | **이벤트형 캡처**(제품 부하) |
| m3 ↔ m4 | 같음 | **연속 캡처**(상한) |
| m4 ↔ m5 | 같음 | 카메라 최대부하에서 WiFi 제거 — m0↔m1 과 **같은 방향·같은 크기**인가 |
| m3 ↔ m6 | 같음 | WiFi 만 다른 쌍 하나 더 (m0↔m1 · m4↔m5 와 세 번째 대조) |
| m6 ↔ m7 | 같음 | **해상도**(프레임이 커지면 마이크가 흔들리는가) |
| 첫 m0 ↔ 끝 m0 | 같음 | **세션 드리프트** — 여기서 어긋나면 위 전부 무효 |

- `gap` 이 0 이 아닌 창은 마이크가 실제로 끊긴 창이다. **clip 비교 이전에 이것부터 본다** — 끊긴 창의 `n` 은 작아지고 통계가 흔들린다.
- `pk` 가 m0 에서 이미 32768 이면 기준선부터 클램프에 닿아 있다는 뜻이다(6.3(n) 그대로). 그때는 절대값이 아니라 **`clip` 수의 증감**으로 본다.
- `rms` 는 올라가는데 `rmsx` 는 그대로면, 늘어난 것은 **음향이 아니라 클램프**다.

### 6-2. 카메라

- `nul`(fb_get NULL) 과 `soi`(JPEG 아님) 는 **0 이 정상**이다. 0이 아닌 창이 어느 모드에서 나오는지 적는다(카테고리 17 `#620 fb_get fail` 인지와 같은 축).
- `cap len` 은 QVGA 에서 32.2 의 「~6KB」와 같은 자릿수여야 한다. m7(VGA)에서 몇 배가 되는지가 설계 U2 의 입력이다.
- `cap ms` 가 m4(연속)에서 m3(주기)보다 크게 늘면 캡처가 서로를 기다리고 있다는 뜻이다.

### 6-3. ToF · 메모리 · 전원

- `tof fr` 이 모드에 따라 떨어지면 Core 0 경합이 실재한다는 신호다(`err` 이 같이 오르는지 함께 본다).
- `stk m/t/l` 이 창을 거듭하며 **단조 감소**하면 스택이 잠식되는 중이다. 값이 수백 아래로 내려가면 즉시 중단(9절).
- `psram`/`heap` 이 창마다 줄면 누수다. 모드를 왕복시켰을 때(m7→m0→…) 돌아오는지 본다.

### 6-4. 재부팅 식별법

세션 중에 **부팅 배너가 다시 뜨면 보드가 재부팅한 것**이다. 그 줄의 `reset=` 값을 본다:

| `reset=` | 이름 | 뜻 |
|---|---|---|
| 1 | `POWERON` | 전원 인가 — 정상 시작 또는 USB 재연결 |
| 3 | `SW` | `esp_restart` |
| 4 | `PANIC` | 예외/패닉 — 코드 문제 |
| 5·6·7 | `INT_WDT`/`TASK_WDT`/`WDT` | 워치독 — 어떤 태스크가 굶었다 |
| **9** | **`BROWNOUT`** | **전원 전압 하강 — 이 하네스가 찾는 것 중 하나** |

`reset=9` 가 어느 모드에서 나오는지가 곧 「그 부하가 전원을 무너뜨린다」의 직접 증거다. 기록에 **모드와 함께** 적는다.

## 7. 호스트 단위 검증 (하드웨어 없이 언제든 재실행)

```
cd <repo>
c++ -std=c++17 -Wall -I firmware/include -o /tmp/cpt firmware/tools/camera_probe_test.cpp && /tmp/cpt
```
기대: `camera_probe_test: 97 checks passed`

### 7-1. negative control 6종 — **각각 반드시 실패해야 한다**

가드를 하나씩 지우고 테스트가 그것을 잡는지 본다. 지운 뒤에는 **반드시 원복**한다.

| NC | 지우는 가드 (`firmware/include/…`) | 깨는 불변식 | 결함 조건(무엇이 조용히 지나가는가) | 잡아야 할 단언 |
|---|---|---|---|---|
| NC-1 | `probe_stats.h` `return buf[0] == 0xFF && buf[1] == 0xD8;` → `return buf[1] == 0xD8;` | 선두 **2바이트 모두** 확인 | 첫 바이트만 다른 버퍼를 JPEG 으로 오인 → 서버 400 을 보드가 미리 못 거른다 | `probeIsJpegSoi(first, 2) == false` |
| NC-2 | `probe_stats.h` `if (buf == nullptr \|\| len < 2)` → `if (buf == nullptr)` | 버퍼 너머를 읽지 않는다 | 길이 0·1 버퍼에서 `buf[0]`·`buf[1]` 을 읽는다 | `probeIsJpegSoi(good, 0/1) == false` |
| NC-3 | `probe_stats.h` `return w != nullptr && w->ok != 0;` → `return w != nullptr;` | 표본 0건 창은 표본이 있다고 보고하지 않는다 | 캡처가 한 번도 안 된 창이 **`len=0 ms=0/0/0`** = 「0ms 에 성공」처럼 읽힌다 | `probeCamHasSample(&w) == false` |
| NC-4 | `probe_modes.h` `case 7:` 의 `PROBE_CAM_PERIODIC` → `PROBE_CAM_CONTINUOUS` | 인접 모드는 한 변수만 다르다 | 악화 원인을 한 변수로 귀속할 수 없게 된다 | `probeModeDiffCount(a, b) == 1` |
| NC-5 | `probe_stats.h` `if (w->ok == 0) {` → `if (false) {` | 최소/최대는 첫 표본으로 세운다(센티넬 없음) | 첫 표본이 들어와도 `len_min`·`ms_min` 이 0 에 머문다 | `w.len_min == 6000 && w.len_max == 6000` |
| NC-6 | `probe_modes.h` `PROBE_NONADJ_PAIRS` 의 `{3, 6}` → `{2, 6}` | 런북 6-1 표의 **비인접** 쌍도 한 변수만 다르다 | 표에 두 변수 다른 쌍이 올라가 「WiFi 축 세 번째 대조」가 조용히 거짓이 된다 | `probeModeDiffCount(probeModeCfg(p.a), probeModeCfg(p.b)) == 1` |

⚠️ **함정 예고** — 아래 케이스가 테스트에서 빠지면 그 NC 는 통과해버린다(= 단언이 무디다):
- NC-1 은 「**첫 바이트만** 다른」 케이스가 있어야 잡힌다.
- NC-2 는 「길이 1 + **뒤 바이트가 0xD8**」 케이스가 있어야 잡힌다.
- NC-4 는 인접 쌍을 **전부** 순회해야 잡힌다(한 쌍만 보면 깨진 표가 통과한다).
- NC-6 은 **쌍 표**를 변형해야 새 단언에만 걸린다. 모드 테이블 쪽(예: `case 6:` 의 `wifi_tx` 를 `true` 로)을
  건드리면 인접 사슬이 먼저 깨져 NC-4 의 단언이 잡아버리므로, 새 단언의 독립 검출을 확인할 수 없다.

미검출이면 「가드 없음」이라고 결론짓기 전에 3확인: ① 도구 생존(baseline 이 통과하는가) ② 도달 가능성(그 코드가 실제로 불리는가) ③ 단언 무딤(위 함정).

### 7-2. 런타임 NC (하지 않음)

「`fb_return` 제거 → fb 고갈 관측」 같은 변형은 **보드 플래시가 필요**하므로 이 문서의 범위에서 **도달 불가**로 분류한다.
호스트 테스트로는 `esp_camera_*` 를 부를 수 없고, 스텁을 만들면 재는 대상이 스텁이 된다.

## 8. 실패 시 로그 대응표

| 증상 | 뜻 | 대응 |
|---|---|---|
| `[cp][mN] set … init=0` 인데 `cam≠0` | 카메라 init 실패 | 직전 `[CAMERA] esp_camera_init failed: 0x…` 을 본다. `0x105` = 카메라 미검출(FPC 재결합) |
| `framesize … rc≠0` 또는 `camres≠res` | 해상도 변경 실패 | 그 구간의 해상도 축 무효. 기록에 적고 m7 을 다시 시도 |
| `net st≠3` | WiFi 끊김 | WiFi 축(m1~m4) 무효. 핫스팟 확인 후 재부팅하고 세션을 처음부터 |
| `txerr` 만 증가 | 송신 실패 | 목적지 LAN 주소가 현재 핫스팟과 다른 대역일 수 있다. `secrets.h` 의 값과 노트북 `ipconfig getifaddr en0` 대조 |
| `tx` 는 오르는데 m0↔m1 차가 전혀 없음 | **WiFi 축이 죽었을 수 있음** | `txerr=0` 은 무선 송신 성공을 보장하지 않는다(ARP 미해결 시 lwIP 가 큐에 담고 성공을 돌려줌 — 2-1 절). 2-1 ①~③ 을 다시 하고, 통과하는데도 차가 없으면 그때가 **실제 관측 결과**다 |
| `mic gap≠0` | `i2s_read` 실패 | 그 창은 버린다. 계속 나오면 마이크 결선(6.3(a)) |
| `mic n` 이 160,000 에서 크게 모자람 | 마이크가 굶었다 | Core 0 경합 후보. 그 모드를 기록하고 계속 |
| `tof err` 급증 | I2C 읽기 실패 | ToF 축 무효. 9.1(b) 결선 |
| `cam nul≠0` | `fb_get` NULL | 카테고리 17 `#620`. 어느 모드에서 나오는지 적는다 |
| `stk` 수백 이하로 하강 | 스택 잠식 | **즉시 중단**하고 9절 |
| 부팅 배너 재출력 + `reset=9` | 브라운아웃 | 그 모드·그 시점을 적는다. **이 세션의 핵심 관측 중 하나다** |
| 부팅 배너 재출력 + `reset=4/5/6/7` | 패닉·워치독 | 코드 문제. 중단하고 9절 |

## 9. 정지 트리거 (보고 후 사용자 판단)

- `reset=4`(PANIC) 또는 워치독 재부팅이 반복된다
- `stk` 가 계속 줄어 수백 바이트 이하로 내려간다
- 첫 m0 와 마지막 m0 가 자릿수 단위로 다르다(세션 드리프트 — **그 세션 전체를 버린다**)
- `mic init 실패` 로 최우선 질문 자체가 성립하지 않는다
- 카메라가 어떤 모드에서도 init 되지 않는다

## 10. 이 하네스가 바꾸지 않는 것

- 제품 코드 0줄. `camera_common` · `mic_common` · `tof_common` · `uplink_common` · 기존 11개 env 무접촉.
- 서버 API 호출 0(`/detect`·`/enrich` 포함), 카카오·NCP 0, 외부 인터넷 송신 0(핫스팟 LAN 내 UDP 더미만).
- 판정·임계값 0. 6.3(n) 해결책 선택 0 — **사용자 판단 대기 그대로**.
- 해상도·녹음 길이·타임아웃 확정 0 — 설계 U1·U2·U3 은 이 결과를 입력으로 **나중에** 정한다.

## 11. 한계 (결과를 읽을 때 함께 적어야 하는 것)

- **소프트웨어 관측이라 전원 레일 전압을 직접 못 본다.** 브라운아웃은 `reset=9` 로 **사후에만** 드러나고, 재부팅에 이르지 않는 전압 딥은 보이지 않는다. 오실로스코프 없이는 여기까지다.
- **디지털 관측만이다.** 마이크 잡음이 전기적 유입인지 음향인지 이 하네스는 가르지 못한다(그 분리는 `env:mic_noiseprobe` 의 m0~m6 몫).
- **실 음향 조건이 통제되지 않는다.** 방음실이 아니므로 절대값은 세션 간 비교 불가. 그래서 5절이 같은 세션 안의 모드 대조와 m0 복귀를 강제한다.
- **`cap ms` 는 `millis()` 해상도(1ms)다.** 1ms 미만 차이는 보이지 않는다.
- **`txerr=0` 은 「무선으로 나갔다」를 뜻하지 않는다.** ARP 가 안 풀린 대상이면 lwIP 가 패킷을 큐에 담고 성공을 돌려준다(2-1 절). WiFi 축 결과를 적을 때는 2-1 ①~③ 을 통과한 세션인지 함께 적는다.
- **UDP 더미는 실 업로드가 아니다.** 실제 2차 업로드는 수백 KB 를 수백 ms 에 몰아 보내므로 순간 전류 프로파일이 다르다. 여기서 「WiFi 영향 없음」이 나와도 PR-B 의 실 전송에서 다시 봐야 한다.
