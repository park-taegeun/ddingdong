## 1. 전제

- 보드 재플래시가 먼저다(지금 보드에 무엇이 올라가 있든 `enrich_autotrig`로 덮는다).
- `firmware/include/secrets.h`가 실제 서버를 가리켜야 한다. **실값을 로그 · 문서 · PR 본문에 남기지 말 것.**
- **수동 · 자동이 5초 안에 섞이면 서버가 429를 낼 수 있다**(6.1 rate limit = 같은 device 5초당 1회). 자동끼리는 79버퍼(5,056ms) 간격이 보장되지만 수동 `s`는 막지 않는다(경로 무변경, I2). 그래서 **`s`는 마지막 자동 트리거 뒤 6초 이상 지나서** 친다.
- 세션 상한 12(enrich_wire.h)는 그대로다. 자동 트리거가 무음에서 연달아 나면 상한이 일찍 찰 수 있으므로 `sent=n/12`를 본다.
- 포트는 하나만 쓴다. 모니터를 켠 채로 업로드하지 말 것.

## 2. 빌드 · 플래시 · 모니터 (분리 실행)

```
cd firmware
~/.platformio/penv/bin/pio run -e enrich_autotrig -t upload
mkdir -p ~/ddingdong-측정결과/$(date +%F)/enrich_autotrig
script -a -F ~/ddingdong-측정결과/$(date +%F)/enrich_autotrig/autotrig_runtime.log \
  ~/.platformio/penv/bin/pio device monitor -b 115200 -f time
```

- `-f time` = 줄 앞에 호스트 수신 시각을 붙인다. `script -a -F` = 이어쓰기 + 즉시 플러시.
- 모니터를 연 뒤 **보드 USB-C 옆 R 버튼**(물리 버튼, RESET)을 한 번 눌러 부팅 줄부터 남긴다. **모니터 키 `s`**(키 입력, 수동 트리거)와 헷갈리지 말 것.

부팅 기대(발췌):
```
[BOOT] ddingdong enrich autotrig (M5-c ⓑ 자동 + 수동 's')
[BOOT] autotrig T=450 pre=8 refr=79buf mask=32/2
[uplink] PSRAM alloc OK tag=enrich-rec bytes=196608
[uplink] PSRAM alloc OK tag=enrich-body bytes=709632
[BOOT] rec=196608B 6144ms ebody=709632B
[BOOT] client_request_id nonce=xxxxxxxx
[BOOT] micEnrichTask started (Core 0) — POST 는 loop 태스크
```
`T=450 pre=8 refr=79buf mask=32/2`가 아니면 빌드가 잘못된 것이다. 정지하고 보고한다.
`rec=196608B 6144ms ebody=709632B`가 아니면(예: `163840B 5120ms`) 2차 녹음 연장(12절)이 빌드에 안 들어간 것이다. 역시 정지하고 보고한다. `PSRAM alloc FAILED`가 나와도 정지한다(연장분 PSRAM +65,536 B는 빌드로 증명되지 않는다).

## 4. 새 로그 줄 (전부 loop 태스크가 낸다 — 마이크 태스크 Serial 추가 0줄. 각 줄 ≤80B, 6.3(j))

| 줄 | 언제 | 최악 길이 |
|---|---|---|
| `[e2a] k=<k> v1=<v1> ok snap_at=<k+24> n=<수락 누적>` | 발화를 수락 | 63B |
| `[e2a] k=<k> v1=<v1> ign=<사유> n=<그 사유 누적>` | 발화를 무시(사유 = `busy` · `ring` · `late` · `psram`) | 51B |
| `[e2a] busy=<누적> drop=<누적> ring=<누적> late=<누적>` | 위 두 줄 바로 다음에 매번 | 70B |
| `[e2a] k=<k> win=[<a>,<b>) want=<k−8>` | 자동 건 runEvent 안, `[e2] stk=` 다음 | 63B |

- 수락된 자동 건의 이후 흐름(`[tof][e2]` · `[e2] id=e2a-…` · `d http=` · `gate=` · `cam` · `e http=`)은 수동과 같은 줄이다.
- **불응기에 막힌 버퍼는 로그를 남기지 않는다**(발화 자체가 없다). 「친 횟수 대비 `[e2a] k=` 줄 수」로만 보인다(6절).

## 5. ④런타임 절차 (학부생 몫)

조건마다 런을 하나씩 쓰고, 시작 · 끝 시각을 메모한다(`-f time` 호스트 시각).

### 5-1. 무음 2분 — 런 `21_autosilence_J`
부팅 뒤 30초 이상 지나서 시작한다. 2분 동안 아무 소리도 내지 않는다.
기록: `[e2a] k=` 줄 수(ok / ign 사유별), 마지막 `[e2a] busy=` 줄 값. 오프라인 기준(원본 = trig_wav_analysis/report.md): V1 · T450 · N1 무음 오트리거 0, 무음 V1 최대 417(예외) · 335(예외 제외).

### 5-2. 노크 10회 — 런 `22_autoknock_J`
간격은 **6초 이상**(불응기 5,056ms + 처리 시간). 두드리는 사람이 ToF 정면 1m에 선다.
기록: 친 횟수 10 대비 `ok` 수 · `ign` 사유별 수 · `busy` · `drop`, 각 회차의 `cls=` · `gate=`.

### 5-3. 초인종 — spisafe 10회(런 `23_autobellspi_J`) · 폰 재생 10회(런 `24_autobellphone_J`)
간격과 기록 항목은 5-2와 같다. 거리 · 방향은 회차마다 메모한다.

### 5-4. 수동 `s` 1회 — 런 `25_manual_J` (I2 확인)
마지막 자동 트리거 뒤 6초 이상 지나서 **모니터 키 `s`**를 친다.
기대: `[e2] trigger — 2차 녹음 시작 + 1차 스냅샷 요청` → `[e2] id=e2-…`(접두 `e2-`) → `[e2a] … win=` 줄 **없음**.

### 5-5. 배선 · 시점 · 스택 (모든 자동 건에서)
- `[e2a] k=<k> win=[<a>,<b>) want=<w>`에서 **a == w** 그리고 **b − a == 32**를 본다. a ≠ w면 스냅샷이 밀린 것이다(I1 위반). 정지하고 그 줄 앞뒤 20줄과 함께 보고한다.
- `[e2] stk=<n>` = 마이크 태스크 스택 최저 여유(byte). 수동 · 자동 값을 나란히 적는다(V1 계산 추가분 비교).
- `[e2] stk=… gaps=<n>` = i2s_read 실패 누적. 0이 아니면 슬롯 순번 연속성 가정이 흔들린다(8절 한계).

## 6. 「처리 중 트리거」 관측값 — busy + drop (7.7(l) 재판정 트리거 (1))

7.7(l) 재판정 트리거 (1) 「M5-c 판정 PR에서 2차 대기 중 트리거 누락이 관측될 때」의 관측값은 **두 계수의 합**이다.

| 계수 | 세는 곳 | 뜻 |
|---|---|---|
| `busy` | loop(`autoTrigDecide`) | 발화를 읽었더니 처리 중이었거나(기존 4플래그), 처리 중에 발화했다가 처리가 끝난 뒤 읽혔다 |
| `drop` | 마이크 태스크(`g_trigDrops`) | 앞 요청이 아직 안 읽힌 채(loop가 runEvent로 막혀 있음) 또 발화했다 |

- 읽는 법: 런의 **마지막** `[e2a] busy=<B> drop=<D> …` 줄을 본다. 두 값 모두 부팅 뒤 누적이다.
- 합치는 법: **처리 중 발화 수 = B + D**. 조건 구간별로 보려면 (구간 끝 직후 줄의 B + D) − (구간 시작 직전 줄의 B + D).
- drop은 마이크 태스크가 세지만 출력은 loop가 한다. drop은 앞 요청이 대기 중일 때만 늘고, 그 대기 요청이 처리될 때 `busy=` 줄이 다시 나온다. 그래서 마지막 줄에는 drop이 빠짐없이 들어 있다.
- ring · late는 처리 중 발화가 아니다. 합에 넣지 않는다.

**불응기(발화 기준)의 대가 — 따로 관찰한다.** 무시된 발화도 불응기를 시작시킨다(2026-10-01 17:05 사용자 결정, 오프라인 규칙과 같음). 그래서 **이벤트 처리가 끝난 직후 최대 5초 동안** 새 노크 · 벨은 발화조차 하지 않는다. busy · drop에도 잡히지 않는다. 관찰법은 「사람이 친 횟수 − `[e2a] k=` 줄 수」이고, 0이 아니면 그 회차 시각을 메모한다. 이 값이 0이 아닌 것이 재판정 트리거(이벤트 직후 노크 · 벨 놓침)다.

## 7. 관찰 항목 — 2차 자막에 방문자 말이 잘렸는가 (논증만 있음 · 측정 0)

**논증**: 자동 건의 2차 녹음은 loop가 수락한 직후의 슬롯부터 담긴다. 수락 시점은 판정 직후이므로 슬롯은 대략 k+2부터이고, 트리거 버퍼 k가 시작된 뒤 약 128ms다(pre 0 유지). 그래서 **초인종 · 노크 소리 자체가 녹음 앞부분을 차지**한다. 수동은 「소리가 끝난 뒤 `s`」 순서라 녹음이 말부터 시작했다. 같은 5.120초 안에 방문자 말이 담기는 시간은 자동이 더 짧을 수 있다.

- 서버: run_server.sh는 NCP를 제거하므로 **자막이 생성되지 않는다**(3절). `ENRICH_UPLINK_RUNBOOK.md` 1절 서버(실 STT · 실과금 · 세션 상한 12)를 쓴다.
- 방법: 벨(또는 노크) 직후 바로 한 문장을 말한다(예: 「택배 문 앞에 두고 갑니다」). 자동 5회, 수동 5회(소리 끝 → `s` → 말).
- 기록: 회차마다 자막 원문(개인정보가 없는 문장만)과 「문장 앞부분이 잘렸는가 Y/N」.
- **녹음 시작 시점 · 길이 변경은 이 PR 범위 밖이다**(별도 결정, 이 PR의 코드 변경 0).
- [2026-10-05 실측 n=3 · PoC-(67)] 노크 직후 「택배 왔습니다, 문 앞에 두고 갈게요」 → 앞 잘림 0/3 · **뒤 잘림 2/3**. 논증대로 소리가 녹음 앞을 차지했고, 잘린 쪽은 끝이었다. → 녹음 시작 시점은 그대로 두고 **길이만 연장**했다(12절). 연장 뒤 확인 절차 = 12-4.

## 8. 알려진 한계 (④런타임에서만 드러남)

- `i2s_read`가 실패하면 그 버퍼는 링에 적재되지 않고 순번도 늘지 않는다. 그러면 「인접 슬롯 = 시간상 인접」 가정이 깨진다(`gaps` 로그로 보임). 오프라인 파일엔 이런 틈이 없다.
- 짧은 반환(n < 1024)이 오면 슬롯 꼬리에 이전 데이터가 남는다(기존 동작과 같음). V1이 그 꼬리를 포함한다.
- 2차 녹음은 트리거 버퍼보다 약 128ms 늦게 시작한다(7절). 길이는 이 빌드만 6.144초다(12절).
- 연장분 1.024초만큼 녹음 중(= busy) 구간이 길어진다. 그 사이 큰 말소리 · 소음이 V1 > 450이면 `busy`로 계수된다(6절).
- 처리 직후 최대 5초 동안 놓칠 수 있다(6절, 불응기 발화 기준).

- 녹음은 k+2부터라(d = 2) 녹음에 들어가는 소리 ≈ Lp − d = 16버퍼 → 규칙 「≤ 16 → 16 · ≤ 24 → 24 · 초과 → 정지」의 16. **경계값에 정확히 걸렸다**: 다시 측정해 Lp가 19 이상이면 24로 바뀌어야 하므로 재판정 대상이다.
